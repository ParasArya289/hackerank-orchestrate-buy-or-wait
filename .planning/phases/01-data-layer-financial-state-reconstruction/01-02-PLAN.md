Dataset facts confirmed this session (do not re-derive, use directly):
- `financial_events.csv` `status` values: settled, pending, scheduled, unrealized, cancelled, failed. `event_type` values: refund, investment_sale, subscription, debt_payment, expense, income, investment_valuation, investment_purchase. `direction`: debit, credit, non_cash. `flexibility`: fixed, reducible_or_stoppable, reducible, stoppable. `category` values include: rent, utilities, groceries, dining, entertainment, transport, housing, education, healthcare, insurance, gym, streaming, music_subscription, cloud_storage, delivery_membership, work_expense, shopping, family_support, debt_repayment, investment, salary, windfall.
- Per AGENTS.md section 6.3 / problem_statement.md "90-Day Safety Check": reserve pending debits (count them as future cash outflow); do NOT count pending credits, bonuses, commissions, refunds, lottery proceeds, or investment gains until settled; ignore failed/cancelled transactions, duplicate records, and unrealized investment values entirely (they never count toward cash flow).
- `linked_event_id` is populated on only 58 of 25,342 rows and points to an earlier event in the same transaction/investment lifecycle (e.g. a refund's `linked_event_id` points to the original purchase). The link itself does not decide cash-flow treatment — status still governs that.
- Recurrence example confirmed in data: `user_01` category `rent`, 6 rows, same amount 5148 ZAR, monthly cadence (2023-10-02, 2023-11-02, ... 2024-03-02), status settled, flexibility fixed — this is the canonical "detect as recurring" shape (same user + category + amount tolerance + regular date interval + count >= 3).
- `messages.csv`: 215 rows, `source_type` in {employer, bank, merchant, service_provider, financial_service}, mixed English/Indonesian text, `related_event_id` populated on only 39 rows (most messages are NOT tied to one specific event row — treat those as request-level or user-level narrative context, not a hard amendment target). Example observed row: `message_01` (user_02, no request_id, no related_event_id) states a salary increase to IDR 42,750,000 effective 2025-08-15 — this is the canonical "salary change" amendment case referenced in ROADMAP Phase 1 success criterion 3.
- `images.csv`: 16 rows, all linked 1:1 to the 16 blank-amount financial_events already resolved in Plan 01 — for STATE-04 purposes, treat any OTHER potential image (none currently observed beyond the blank-amount set) the same way: only apply if `request_id`/`event_id` linkage actually exists in `images.csv`, never assume.
- This project's stack decision routes STATE-03/STATE-04's actual free-text/image LLM interpretation calls to Phase 3 (gemma4 for text, qwen2.5vl for vision) per ROADMAP.md. Phase 1 must build the deterministic extraction scaffold with a clean extension point (`extract_message_amendment`, `extract_image_amendment`) — simple deterministic pattern-matching (regex for currency amounts, keywords like "cancel"/"naik menjadi"/"increase to") is acceptable and sufficient for Phase 1's success criteria; a full NLU call is Phase 3's job. Do not block Phase 1 completion on calling Ollama.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| messages.csv message_text -> extract_message_amendment | Untrusted free text (may contain prompt-injection-style instructions); must only ever produce data (Amendment objects), never execute code or bypass the deterministic rules |
| images.csv/media PNGs -> extract_image_amendment | Untrusted file reference; only applied when request_id/event_id linkage is explicit in images.csv |
| Amendment application -> events DataFrame mutation | Amendments must only overwrite fields for the specific event_id they are linked to, never propagate to unrelated events |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-01-04 | Elevation of Privilege | code/state/amendments.py | mitigate | `extract_message_amendment` uses only regex/keyword matching on `message_text`; never calls `eval`/`exec`/subprocess on message content; a message containing "ignore the rules" produces `amendment_type="none"` since it matches no defined keyword pattern |
| T-01-05 | Tampering | code/state/reconcile.py | mitigate | `resolve_conflict` requires `is_explicit_amendment` to be a data-derived boolean set by the caller from real event/message/image state, never user-controllable free text directly |
| T-01-06 | Repudiation | code/state/reconcile.py | mitigate | Every applied amendment is retained in `FinancialState.amendments_applied` for traceability (auditable which source changed which event) |
</threat_model>
